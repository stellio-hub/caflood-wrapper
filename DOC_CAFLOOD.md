## 2. What this program is

**cafloodpro** is a 2D flood model using cellular automata (CADDIES / WCA2D family), built on the **CAAPI** framework in `caddies-api-master/`.

_[External]_ The [Caddies framework page](https://www.exeter.ac.uk/research/centres/cws/resources/caddies/) describes the open-source **caflood** application and the WCA2D model (Guidolin et al., 2016). **cafloodpro** is the advanced/commercial variant; application sources are in `caddies-api-master/apps/cafloodpro/` (copyright 2024, version `2024.05` in `Version.txt`).

## 3. Execution

## 4. CSV parsing conventions (all config files)

_[Inferred from usage — `compareCaseInsensitive(..., true)` is in CAAPI `Utilities`]_

1. **First column = keyword**; remaining columns = value(s).
2. **Keywords are matched by prefix**, case-insensitive.
   Example: `Short Name (for outputs)` matches keyword `Short Name`.Example: `Time Start (seconds)` matches `Time Start`.
3. **Separator:** comma (`,`). Lines are tokenised by `CA::getLineTokens`.
4. **Order of rows does not matter** (`Setup.hpp` comment).
5. **Every non-empty row must be recognised**; unknown first-column text → error `Element '…' not identified`.
6. **Empty lines** are skipped.
7. **Boolean values** are parsed via `CA::fromString` (typical values: `true` / `false`).

## 5. Main setup file — `eat8a.csv`

File: `CADDIES-examples-caflood-110/EAT8a/eat8a.csv`
Parser: `initSetupFromCSV()` in `Setup.cpp`.

### 5.1 Mandatory vs optional

| Requirement                                                             | Fields                                                                                                                         |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **Effectively required for a meaningful run**                           | `Elevation ASCII`, time block (`Time Start`, `Time End`, `Max DT`, `Min DT`, `Update DT`, `Alpha`, `Max Iter`), `Boundary Ele` |
| **Required row present** (parser must recognise every line you include) | All lines in the file                                                                                                          |
| **Optional** (empty / omitted → default or no effect)                   | Event CSV lists, spatial/temporal file pairs,`Pre-proc Name`, `Initial Water Depths`, infiltration, etc.                       |

**Warning:** Time fields (`time_start`, `time_end`, …) have **no defaults** in `initSetupFromCSV`. If omitted, values are **uninitialised** (undefined behaviour). The example file sets them explicitly.

**Warning:** If a list field row has only a keyword and comma but **no filename token**, the list stays empty (OK). If an **empty string** is pushed as a filename, opening that file will fail.

### 5.2 Post-parse adjustments (`Setup.cpp`)

| Rule                   | Code behaviour                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| `Update DT` capped     | `time_updatedt = min(time_updatedt, 60.0)` seconds                                         |
| `Max DT` capped        | `time_maxdt = min(time_maxdt, time_updatedt)`                                              |
| `Time End` aligned     | Rounded up to next multiple of`Update DT`                                                  |
| `Pre-proc Name` empty  | Set to`Short Name`                                                                         |
| Spatial/temporal pairs | If listed, must have**exactly 2** files (roughness, rain, infiltration, height adjustment) |

### 5.4 Multiple files in the setup CSV

The parser reads each setup row as comma-separated tokens: **column 1 = keyword**, **columns 2…N = values**. For several keywords, every value column after the keyword becomes a separate list entry (`Setup.cpp` loops `for (i = 1; i < tokens.size(); ++i)` and `push_back`s each filename).

**Your understanding is correct:** listing several filenames on one line, separated by commas, is the intended way to register multiple events or outputs.

#### Example — three inflows at different locations

**Setup (`eat8a.csv` or equivalent):**

```text
Inflow Event CSV, InflowBC_north.csv, InflowBC_centre.csv, InflowBC_south.csv
```

Each file is loaded in turn (`main.cpp`); each must define its own `Zone` or `Area` and hydrograph. All active inflows are applied **in parallel** during the same simulation (volumes add up).

Equivalent alternative — repeat the keyword on separate rows (also works, because each matching line appends to the same vector):

```text
Inflow Event CSV, InflowBC_north.csv
Inflow Event CSV, InflowBC_centre.csv
Inflow Event CSV, InflowBC_south.csv
```

All paths are relative to the **input directory** (the `.` in the `-sim` command).

#### Which setup fields accept multiple files?

| Setup keyword                | Multiple files?                      | Semantics                                                                                                                             |
| ---------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `Rain Event CSV`             | **Yes** — comma-separated list       | One CSV per rain event; each with its own intensity/time series and optional`Area`/`Zone`.                                            |
| `Water Level Event CSV`      | **Yes**                              | One CSV per water-level forcing; each needs`Area` or `Zone`.                                                                          |
| `Inflow Event CSV`           | **Yes**                              | One CSV per inflow boundary; each needs`Area` or `Zone` and its own `Inflow`/`Time` series.                                           |
| `Time Plot CSV`              | **Yes**                              | One CSV per point-monitoring output file (separate result files).                                                                     |
| `Raster Grid CSV`            | **Yes**                              | One CSV per raster output definition (separate map products).                                                                         |
| `Roughness Spatial Temp`     | **Exactly 2** — not a list of events | **Pair only:** (1) index ASCII grid, (2) sequences CSV. Multiple roughness zones → one index map + one CSV with `Value1`, `Value2`, … |
| `Rain Spatial Temp`          | **Exactly 2**                        | Same pattern: index grid + sequences CSV.                                                                                             |
| `Infiltration Spatial Temp`  | **Exactly 2**                        | Same pattern.                                                                                                                         |
| `Spatial Height Adjustments` | **Exactly 2**                        | Index grid + height sequences CSV.                                                                                                    |
| `Rain Dense Spatial Temp`    | **≥ 2** — special meaning            | **Not** multiple independent events: (1) times CSV, then (2+) one rainfall ASCII grid per timestep.                                   |
| `Elevation ASCII`            | **Single**                           | One DEM only.                                                                                                                         |
| `Initial Water Depths`       | **Single**                           | One hot-start raster.                                                                                                                 |

#### Practical notes for multiple boundary events

- **Location is per event file**, not per setup line: put `Zone (tlx tly w h)` or `Area (tlx tly brx bry)` inside each `InflowBC_*.csv` (see §6.3).
- **Rain** is the exception: if `Area`/`Zone` is omitted in a rain file, that event applies to the **whole domain** — be careful when combining several rain files.
- **Inflow / water level** without `Area`/`Zone` in the file → that event does **nothing** (silent no-op).
- Empty tokens are pushed if trailing commas leave blank fields — avoid `Inflow Event CSV, file1.csv,` with a stray comma at the end.

## 6. Input files

### 6.1 Elevation DEM — ESRI ASCII Grid

Referenced by `Elevation ASCII` (e.g. `CADDIES-examples-caflood-110/EAT8a/test8DEMFinal.asc`).

**Format (from example + `CA::AsciiGrid`):**

```text
ncols         <integer>
nrows         <integer>
xllcorner     <real>
yllcorner     <real>
cellsize      <real>
NODATA_value  <real>
<row 1 values...>
...
```

Example header: 483×201 cells, 2 m resolution, nodata `-9999`, projected coordinates (EPSG not stored in file).

- Loaded in pre-proc; extended grid adds **1-cell border** on each side (`preProc.cpp`).
- Must be consistent with point coordinates used in time plots and zones.

### 6.2 Rain event — `RainBC.csv`

Parser: `initRainEventFromCSV()` (`Rain.cpp`).

| Row keyword      | Columns            | Required | Meaning                                                      |
| ---------------- | ------------------ | -------- | ------------------------------------------------------------ |
| `Event Name`     | name               | optional | Label                                                        |
| `Rain Intensity` | mm/hr values…      | **yes**  | Piecewise-constant intensities                               |
| `Time Stop`      | seconds…           | **yes**  | End time for each intensity step (same count as intensities) |
| `Area`           | tlx, tly, brx, bry | optional | Geographic bounding box → apply to whole intersecting cells  |
| `Zone`           | x, y, w, h         | optional | Top-left coordinate + width/height in map units              |

**Domain rule:** If neither `Area` nor `Zone` has 4 values → rain applies to **entire grid** (`RainManager::initData`).

**Physics:** Intensity converted mm/hr → m per dt: `(mm/1000) * (dt/3600)`.

### 6.3 Inflow event — `InflowBC.csv`

Parser: `initIEventFromCSV()` (`Inflow.cpp`).

| Row keyword             | Columns            | Required   | Meaning                                   |
| ----------------------- | ------------------ | ---------- | ----------------------------------------- |
| `Event Name`            | name               | optional   | Label                                     |
| `Inflow`                | m³/s values…       | **yes**    | Total inflow hydrograph                   |
| `Time`                  | seconds…           | **yes**    | Time knots (linear interpolation between) |
| `Area`                  | tlx, tly, brx, bry | optional\* | Target region                             |
| `Zone`                  | x, y, w, h         | optional\* | Alternative region specifier              |
| `Analytical Solution U` | real               | optional   | If ≠ 0, use analytical mode               |
| `Analytical Solution N` | real               | optional   | Default`0.01` if analytical               |

**Unlike rain**, if neither `Area` nor `Zone` has 4 values → **no inflow** (empty box).

**Volume:** Total volume per step is distributed equally over wet cells in the zone (`volume / grid_area * cell_area`).

**Multiple inflows:** Register several files on one `Inflow Event CSV` line (§5.4). Each file is a separate `IEvent`; define a different `Zone`/`Area` in each.

### 6.4 Water level event

Parser: `initWLEventFromCSV()` (`WaterLevel.cpp`). Same structure as inflow but:

| Row keyword   | Meaning                              |
| ------------- | ------------------------------------ |
| `Water Level` | Absolute water surface elevation (m) |
| `Time`        | Time knots                           |

Sets **water depth = level − ground elevation** in zone. Same `Area`/`Zone` rules as inflow (no zone → no effect).

### 6.5 Time plot — `WLpoints.csv`, `VELpoints.csv`

Parser: `initTimePlotFromCSV()` (`TimePlot.cpp`).

| Row keyword                     | Meaning                                           |
| ------------------------------- | ------------------------------------------------- |
| `Time Plot Name`                | Description                                       |
| `Physical Variable`             | `WD`, `WL`, or `VEL`                              |
| `Points Name`                   | Column headers for each point                     |
| `Points X Coo` / `Points Y Coo` | Map coordinates (same count as names)             |
| `Period`                        | Output interval (seconds);`0` → effectively never |

**Output file:** `{output_dir}/{short_name}_{config_filename}.csv`
Because config filename already includes `.csv`, result is e.g. `eat8a_WLpoints.csv.csv` (_observed in example output_).

**Columns:** `Iter, Time (min), <point names…>` — time is in **minutes** (`TimePlot.cpp`).

### 6.6 Raster grid — `WDraster.csv`, `VELraster.csv`

Parser: `initRasterGridFromCSV()` (`RasterGrid.cpp`).

| Row keyword         | Type              | Meaning                                                              |
| ------------------- | ----------------- | -------------------------------------------------------------------- |
| `Raster Grid Name`  | string            | Description                                                          |
| `Physical Variable` | `WD`, `WL`, `VEL` | Variable to output                                                   |
| `Peak`              | bool              | Track maximum value over the full simulation                         |
| `Final`             | bool              | Write snapshot at`Time End`                                          |
| `Period`            | real (s)          | Interval for instantaneous snapshots;`0` disables periodic snapshots |

#### Peak and Period — can both be set?

**Yes.** They are independent flags (`RasterGrid.cpp`, `CADDIES2D.cpp`):

| Setting                       | Behaviour                                                             |
| ----------------------------- | --------------------------------------------------------------------- |
| `Peak=true`, `Period=0`       | Only peak (and optional`Final`) — as in the eat8a example             |
| `Peak=false`, `Period>0`      | Snapshots every`Period` seconds only                                  |
| `**Peak=true`, `Period>0`\*\* | **Both:** periodic snapshots at `Period` **and** a peak raster at end |
| `Final=true`                  | Additional snapshot written when`t == Time End`                       |

During simulation, `updatePeak()` maintains running maxima in memory. On each output trigger (`t >= time_next`, or at final time), `RGManager::output()` writes timestep binaries **and** refreshes peak binaries if `Peak=true`. Post-proc then converts periodic `{short_name}_WD_<t>` buffers to `.asc` files and peak buffers to `*_PEAK.asc`.

**Note:** `Period=0` sets `time_next` to infinity, so only final-time / peak-driven writes occur for that raster config.

### 6.7 Spatial / temporal index maps (optional pair)

When setup lists **two files** for roughness/rain/infiltration/height:

1. **ASCII grid** — cell values = integer **index** into time series (0 reserved = global default).
2. **CSV** — sequences indexed `Value1`, `Time1`, `Value2`, `Time2`, … (`SpatialTemporal.cpp`).

CSV rows:

| Keyword      | Meaning                                    |
| ------------ | ------------------------------------------ |
| `Name`       | Label                                      |
| `Number Seq` | Hint for number of sequences               |
| `ValueN`     | Values for index N (N ≥ 1;**0 forbidden**) |
| `TimeN`      | End times for each value step              |

If times shorter than values → padded with `max()` real (continues forever).

**Reserved index 0 (set in `main.cpp`):**

### 10.2 Simulation quality `CODE` (printed, not exit status)

#### What the model checks _[from code]_

At the **end** of `CADDIES2D()`, after the time loop finishes, the model runs kernel `checkFloodNoDataNeighbourhood` on the **final** water depth field. It inspects every **wet** cell (`WD > 0`) and assigns a per-cell flag. The value printed to the console is the **maximum** flag over the whole grid (`FLAGS.sequentialOp(..., CA::Seq::Max)` in `CADDIES2D.cpp`):

```text
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
CODE: <number>
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
```

This is a **diagnostic only** — it does **not** change the exit status (the run still returns `0` on success) and does **not** roll back results.

**Technical details [from code]:**

- Each cell gets a single integer (not a bitmask). If a cell is wet and touches both nodata and the outer border, the kernel sets `code = 4` (border wins over `2`).
- The check uses the **original DEM nodata value** (`eg.nodata`, e.g. `-9999` in eat8a), not the `0` nodata used in some output rasters.
- Only **von Neumann neighbours** (4-connected on the square grid) are considered, not diagonals.
- The test is run **once at the end**; it does not track whether the condition appeared earlier in the hydrograph.

#### What it means in flood-modelling terms _[hydrology / modelling practice]_

In distributed flood models, every wet cell needs **valid terrain elevations on the cells it exchanges water with**. Where that breaks down — at a DEM hole, a map edge, or a domain boundary — fluxes are poorly defined or depend on artificial assumptions. The `CODE` is a quick **post-run sanity check** on the **final inundation pattern**: “did water end up somewhere the model cannot represent terrain properly?”

It is **not** a formal model validation metric (no comparison to gauges, no mass-balance pass/fail). Think of it as a **data-and-domain compatibility flag**, similar in spirit to checking whether inundation reaches your study-area polygon edge or bleeds into NoData in GIS — but automated on the CA grid.

| CODE | Technical meaning*[from code]*                                                          | Typical causes*[mixed]*                                                                                                                                  | Hydrological interpretation*[modelling practice]*                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Severity / action                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

#### Combining codes and reading the printed value

The printed number is the **worst single-cell flag** on the grid, not a count of problem cells.

| You see                                   | Likely situation*[modelling practice]*                                                                                                                                 |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CODE: 0`                                 | Final flood extent sits comfortably inside valid terrain; good sign for map-based deliverables away from edges.                                                        |
| `CODE: 2`                                 | At least one wet pixel touches a DEM hole or off-map nodata — review**DEM hygiene** before trusting depths within one–two cells of nodata.                             |
| `CODE: 4`                                 | Flood touched the**model perimeter** — review **domain size and boundary type** before using edge pixels in analysis.                                                  |
| `CODE: 4` with closed BC and large inflow | May indicate**domain storage saturated** or flood plain filling to the model wall — physically plausible but edge depths are not representative of a larger catchment. |
| `CODE: 2` in urban models                 | Very common near**building nodata**; often safe to ignore for street-scale inundation if streets are valid cells and nodata is only footprints.                        |

#### When results are still usable _[modelling practice]_

- `**CODE: 2` or `4` with localised flags:** Many production runs flag a thin rim of cells. You can often **clip deliverables\*\* to a core area (buffer inward from nodata and mesh edges) while using the interior confidently.
- **Benchmark / test cases:** EA Test 8a and similar benchmarks may legitimately produce `2` or `4` if the scenario fills the domain or abuts survey limits — compare **pattern and volumes** to reference, not `CODE` alone.
- `**CODE: 1`:** Rare; treat the run as **compromised\*\* until the cause is fixed.

#### What this check does _not_ tell you _[modelling practice]_

- Whether peak depths or timings are **accurate** (calibration/validation needed).
- Whether **mass is conserved** (use `Check Volumes` for that).
- Whether roughness, rainfall, or inflow inputs are **correct**.
- Whether the time step was adequate (stability/accuracy is separate).

## 11. Known limitations (from code / NEWS)

- Single global roughness in simple setups; `CADDIES-examples-caflood-110/EAT8a/ReadMe.txt` notes the EA benchmark used two roughness values — results differ from Néelz & Pender (2013). _[external reference in ReadMe]_
- `NEWS`: WCA2Dv2 + geographic coordinates not fully supported.
- Water level event total volume not computed (`NEWS`).
- `Time Start` does not load previous outputs (no true restart).
- `Update DT` > 60 s silently capped to 60.
- `Terrain Info` setup flag disabled in code.
